# Производительность: почему лагает к 5-му раунду

## Диагноз

Дело было не в количестве зомби и не в «тяжёлом рендере».

`update` стоит 0.2–0.6 мс на кадр и почти не растёт от раунда — физика тут ни при чём.
Весь кадр — это `draw`, а внутри него три четверти — свет (`lighting.js`).

А ломалось всё из-за утечки, которая включалась **ровно тогда, когда игрок
включает генератор** — то есть как раз на 3–5 раунде, когда набираются очки.

`glowSprite()` кэшировал спрайты свечения по **строке цвета целиком**. А цвет
ему передавали с альфой, которая каждый кадр новая: у перк-машин это
`0.30 * pulse` от синуса, у взрывов — затухающий `k`. Итог:

| | было |
|---|---|
| новых canvas на кадр | **12** |
| новых `createRadialGradient` на кадр | **12** |
| памяти в секунду | **~46 МБ** |
| удержано через 20 с игры | **~1.9 ГБ** |

Кэш ничего не освобождал, потому что ключи всё время новые. Через минуту-две
после включения света вкладка живёт на сборке мусора — отсюда «лаги к пятому
уровню», которые только усиливаются.

## Что сделано

1. **Свечения пекутся по RGB, яркость едет в `globalAlpha`.** Под `lighter` это
   то же самое, но кэш больше не растёт: 12 спрайтов на кадр → ноль.
2. **Факел игрока** — был клип + новый градиент каждый кадр, теперь запечённый
   сектор, который просто поворачивается.
3. **Виньетка** запекается один раз.
4. **Аддитивный проход свечений ушёл в половинное разрешение.** Он рисовался
   прямо на сцену 800×500 — ~1.4 Мпкс на кадр. Теперь копится на слое света и
   добавляется одним блитом: в 4 раза дешевле, а глазу разницы нет (свечения —
   мягкие пятна).

Замер `tools/harness/ablate.mjs` (внахлёст, медиана 3×120 кадров, CPU-canvas
с принудительным сбросом), раунд 5, свет включён:

| | было | стало |
|---|---|---|
| кадр целиком | 19.69 мс | **14.95 мс** |
| проход света | 14.68 мс | **10.96 мс** |
| аддитивные свечения | 9.88 мс | **2.79 мс** |
| новых canvas/кадр | 12 | **0** |

Картинка не изменилась: худшее отклонение 3/255, пикселей сдвинутых больше
чем на 2/255 — 0.04%, средняя яркость 49.9 → 50.0.

## Что осталось — варианты

Отсортировано по «польза / риск для картинки».

1. **Слой тьмы в четверть разрешения** (сейчас половина). Остаток прохода света
   — это ~8 мс: дырки от 19–36 огней плюс апскейл 400×250 → 800×500. Четверть
   разрешения срежет это раза в два-три. Цена: тени станут мягче и чуть
   «мыльнее», на резких краях (дверные проёмы) это заметно.
2. **Адаптивное качество.** Считать скользящее среднее кадра и, если оно
   стабильно больше 20 мс, автоматически снижать разрешение слоя света, резать
   частицы и отключать слой крови. Страховка для слабых машин — но это уже
   заметная логика в рендере.
3. **Кэш текста.** 46–56 `fillText` за кадр, каждый с установкой `font`,
   `save`/`restore` и тенью — около 1 мс. Запекать строки в спрайты и блитить.
   Выигрыш умеренный, риск нулевой.
4. **Шаг физики 1/120 → 1/60.** Сейчас `main.js` гонит 120 шагов в секунду;
   при просадке кадров это превращается в 4 шага за кадр вместо двух, то есть
   игра удваивает работу ровно тогда, когда ей тяжело. `update` дешёвый
   (0.2 мс/шаг), так что выигрыш небольшой, но запас по просадкам вырастет
   вдвое. Требует проверки на пролёты сквозь стены.
5. **Слой крови (декали).** ~1.2 мс за кадр и он никогда не очищается — за долгую
   сессию карта заливается кровью целиком. Можно периодически подмывать слой
   (прозрачной заливкой по старому) или держать лимит на число декалей.

## Как мерить

```bash
cd tools/harness && npm i            # тянет только @napi-rs/canvas
node leak.mjs                        # сколько canvas/gradients создаётся на кадр
node ablate.mjs 5                    # стоимость кадра по частям, раунд 5
node soak.mjs 90                     # полторы минуты игры с боем: ошибки, NaN, память
node shotlight.mjs /tmp/a.png && node pixdiff.mjs /tmp/before.png /tmp/a.png
```

Цифры выше — с CPU-canvas, в браузере с GPU всё это быстрее в разы. Но
**счётчики созданий canvas и утечки переносятся один в один**: именно они и были
поломкой, а не миллисекунды.
